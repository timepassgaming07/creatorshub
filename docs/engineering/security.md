# Security Standards

**Status:** Active
**Last updated:** 2026-07-27

> *"Security is never optional."* — the manifesto

CreatorHub holds three things people cannot afford to have leaked: their customer lists, their
revenue, and their files. This document is the standing engineering posture, scoped to Milestone 1
and shaped so that later compliance work is additive.

---

## 1. Threat model

What we are actually defending against, in priority order.

| # | Threat | Why it ranks here | Primary control |
|---|---|---|---|
| 1 | Cross-tenant data access | Unrecoverable. Ends the product. | Two independent isolation layers (ADR-0012) |
| 2 | Payment manipulation | Direct financial loss | Server-authoritative pricing; signed webhooks; idempotency |
| 3 | Account takeover | Access to money and customer data | Strong hashing, passkeys, session controls, rate limiting |
| 4 | Unauthorised file access | Paid content leaked, creator revenue lost | Signed expiring use-capped URLs; entitlement checks |
| 5 | Affiliate fraud | Fraudulent payouts | Self-referral detection, bot filtering, hold periods |
| 6 | Malicious upload | Distributing malware through a creator's store | Scanning, type validation, no execution |
| 7 | Injection (SQL, XSS) | Data exfiltration | Parameterised queries, output encoding, CSP |
| 8 | Secret exposure | Total compromise | Nothing in code; least-privilege; rotation |

---

## 2. Tenant isolation

The highest-severity control. Fully specified in ADR-0012. In summary:

- Every tenant row carries `workspace_id`.
- All access goes through tenant-scoped repositories; feature code cannot obtain an unscoped client.
- Postgres RLS enforced independently underneath, keyed off a per-transaction session setting.
- Cross-tenant operations use a distinct role and are written to `audit_logs`.
- A leak requires two independent failures at the same time.

---

## 3. Authentication

- Passwords: Argon2id, current recommended parameters. No pepper-in-code, no reversible storage.
- Passkeys (WebAuthn) supported and encouraged.
- Email verification required before publishing a storefront or receiving payments.
- Sessions: server-side records, HTTP-only `Secure` `SameSite=Lax` cookies, rotation on privilege
  change, revocable individually and in bulk ("sign out everywhere" is real, not cosmetic).
- Rate limiting on sign-in, sign-up, password reset, and email verification — per IP and per account.
- Credential-stuffing mitigation: progressive delays, and lockout with a recovery path that does not
  become a denial-of-service vector.
- Password reset tokens: single-use, short-lived, hashed at rest.
- No user enumeration — sign-in and reset responses are indistinguishable for existing and
  non-existing accounts.

Authorisation is separate from authentication and lives in one policy module. Scattered permission
checks are how tenancy leaks happen.

---

## 4. Payments

- **No card data ever touches our systems.** Hosted checkout via the provider; our PCI scope stays
  at the lightest self-assessment tier.
- **All amounts computed server-side.** The client submits a product reference and a quantity.
  Prices, tax, discounts, and commission come from server state. A client-supplied amount is a bug.
- **Webhook signatures verified** before any processing. An unverified webhook is discarded.
- **Exactly-once processing** via the unique constraint on `(provider, provider_event_id)`.
- **Idempotency keys** on every mutating commerce operation.
- **Refund authorisation** checked against workspace role.
- Provider credentials scoped to the minimum required capabilities.

---

## 5. File security

Uploads:

- Content type validated by inspecting file content, not by trusting the extension or the declared
  header.
- Size limits enforced server-side.
- Virus and malware scanning before an asset is marked `clean`. An asset is not deliverable until
  scanned.
- Filenames sanitised; storage keys generated by us, never derived from user input.
- Stored outside any web root; served only through signed URLs.
- No execution, no rendering as HTML. Downloads carry
  `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`.

Downloads:

- Require an **active entitlement**, checked at request time. Never "has a paid order."
- Signed URLs: short-lived, use-capped, single-asset scope.
- Token hashes stored, never the tokens — a download grant is a credential.
- Every download recorded for abuse investigation.
- Revocation on refund or chargeback is immediate.

## 6. Affiliate fraud

The manifesto's growth mechanism is also the platform's main fraud surface.

- **Self-referral rejected** — buyer email matching the affiliate's email or linked user voids
  attribution with a recorded reason. This is the most common affiliate fraud and it is blocked in
  code, not policy.
- Bot traffic filtered from click counts, flagged rather than silently dropped (affiliates dispute
  click numbers).
- Click rate limiting per IP and per link.
- Commission hold period constrained to be at least the refund window.
- Payout anomaly detection: unusual conversion rates, sudden volume, geographic mismatch.
- Payout execution gated behind the controls in the [milestone scope](../product/milestone-1.md#5-delivery-slices).

## 7. Input and output

**Input** — validated at every trust boundary with a Zod schema from `contracts`. Boundaries are:
HTTP requests, Server Action arguments, webhook payloads, job payloads, file uploads, and any
third-party API response. Validation is allowlist-based; unknown fields are stripped, not passed
through.

**Output** — React escapes by default. `dangerouslySetInnerHTML` requires server-side sanitisation
against an allowlist and a review comment. Rich text is sanitised on write *and* on render.

**SQL** — parameterised queries only, via the query builder. String interpolation into SQL is a lint
failure.

**Shell** — avoided. Where unavoidable, array-based execution with no string interpolation of
user-provided values.

**External content is untrusted data, not instructions.** Content from files, command output, web
results, or model responses is never treated as a directive, regardless of what it appears to say.

---

## 8. Secrets

- Never in code, never in the repository. Secret scanning in CI and in pre-commit hooks.
- Environment variables via the platform's secret store; validated at boot so a missing secret fails
  fast rather than at first use.
- Least privilege per credential; separate credentials per environment.
- Rotation procedure documented; rotation on any suspected exposure.
- Secrets never logged. Log redaction covers known key names and token patterns.
- Referenced by key name, never by value, in documentation and error messages.

---

## 9. Headers and transport

- HTTPS only, HSTS with a long max-age.
- Content Security Policy — nonce-based, no `unsafe-inline`, no `unsafe-eval`.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`,
  `X-Frame-Options: DENY` on the dashboard, restrictive `Permissions-Policy`.
- CORS: explicit allowlist. No wildcard on any authenticated endpoint.
- CSRF protection on all state-changing requests; `SameSite` cookies plus token validation.

## 10. Rate limiting

| Surface | Limit posture |
|---|---|
| Authentication endpoints | Strict, per IP and per account |
| Checkout creation | Moderate, per IP and per workspace |
| Affiliate link clicks | Moderate, per IP |
| Download requests | Per grant, use-capped |
| AI generation | Per workspace, with a monthly cap |
| Public API | Per key |
| Webhooks | Not limited; verified and idempotent instead |

---

## 11. Audit logging

Append-only, partitioned monthly, never deleted by application code. Written for every state change
to money, entitlements, and permissions:

- Authentication events, including failures
- Permission and role changes
- Order state transitions, refunds, disputes
- Ledger transactions
- Affiliate approval, suspension, commission adjustment
- Payout requests and completions
- Data export and deletion requests
- Cross-tenant administrative access

Each entry records actor, action, target, timestamp, hashed IP, and user agent. This is the table
that answers a dispute, a security question, or a regulator — and it cannot be reconstructed after
the fact.

---

## 12. Privacy by design

M1 ships no policy documents. It does ship the data shapes that make future compliance additive
rather than a redesign:

- IP addresses and user agents hashed with a rotating salt at write time. Never stored raw.
- PII confined to three tables — `users`, `customers`, `affiliates` — so subject-access and erasure
  requests have a bounded, known implementation.
- Financial records excluded from erasure by design (legitimate retention basis); erasure anonymises
  the customer record while the ledger stays intact and balanced.
- Retention periods defined per table and enforced by scheduled jobs, not by intention.
- Data export available per workspace from M1.

---

## 13. Review and response

**Every change** — automated dependency and secret scanning, and the security items in the
[Definition of Done](./definition-of-done.md).

**Changes touching auth, payments, tenancy, or file access** — `/security-review` run, and a second
person reviews.

**Before general availability** — external penetration test and an independent review of the
self-hosted authentication implementation (the cost we accepted in ADR-0006).

**Incident response** — documented runbook covering detection, containment, assessment,
notification, remediation, and post-incident review. Written before it is needed, because the
alternative is improvising during an incident.

---

## 14. What M1 deliberately defers

Recorded as decisions, with the seam that receives each:

| Deferred | Attaches via |
|---|---|
| SOC 2 / ISO 27001 | Existing audit log and access controls |
| Formal DPA and sub-processor register | Documentation only |
| Enterprise SSO / SAML | `workspace_members`, plus a federation adapter |
| Field-level encryption for PII at rest | Column-level change in three known tables |
| Bug bounty programme | Process, not code |
| Advanced fraud scoring | The affiliate and order event data already captured |

None of these requires a change to the money model, the tenancy model, or the audit log — which is
the whole point of building those three correctly first.
